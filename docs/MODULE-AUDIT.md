# Vela — Cross-Cutting Production Audit Synthesis

## 1. Executive Summary

The functional surface of Vela is **not production-ready**. Across 16 audited modules, the read/display layer is consistently well-built (real endpoints, company-scoped queries, good loading/empty states, correct Decimal money math in the backend), but the **action layer is broken module-by-module**: the primary "do something" button — send a reply, register a categorized expense, invite a teammate, emit an invoice/DTE, generate a Vera draft, launch a campaign, create a project — fails or silently no-ops in the majority of modules. The failures cluster into three repeating classes: (a) frontend→backend contract breaks (dead endpoints, field-name/shape mismatches), (b) features that are decorative shells over an unimplemented or unreachable backend, and (c) a status/account/pricing **vocabulary split** where two sides of the app disagree on the same identifier. Two issues are also genuine integrity risks: Marketing breaks multi-tenancy by scoping to `user_id`, and Billing's global "beta" phase grants every tenant unlimited paid access, making checkout cosmetic. The product demos well on read-only screens but cannot complete most of its core daily workflows.

## 3. Cross-Cutting Patterns (repeat across modules)

**P-1 — "Decorative backend" / unreachable engine.** A complete backend feature exists but has zero frontend wiring, so the prominent UI button does nothing:
- Fiscal: `POST /api/fiscal/dte/emitir` called by **no** frontend; the entire DTE emission (the module's reason to exist) is simulated and unreachable. **confirmed.**
- Marketing: publish + platform-connect flow (`publicar`, `google/conectar`, `meta/conectar`, `verificar`) — all dead buttons. **confirmed.**
- Ventas: Verifactu e-invoice toggle + customer captured by UI but backend ignores `contact_id`/`factura_electronica`. **confirmed.**
- Finanzas: full profit_optimizer engine reachable only from `/admin`, not the operator page. **confirmed.**
- Clientes: 6 backend routes (create contact, KB, auto-responses, email connect/sync, generate report, edit) with no caller. **confirmed.**
- Proyectos: create-project / add-task / log-time / add-expense / download-report all exist server-side, none wired (`primary=undefined`). **confirmed.**

**P-2 — Vocabulary / identifier split between the two halves of the app.** The same identifier is spelled differently on each side, so joins silently fail:
- Proyectos: backend logic keys off Spanish statuses (`activo`/`completada`) while real data + frontend use English (`active`/`done`) → every project reports 0% complete, dashboard shows 0 active projects. **confirmed.**
- Costes: category as PGC-code-string (aggregate) vs integer FK (list) → filter returns 0. **confirmed.**
- Contabilidad/Finanzas: hardcoded account codes (`500/510`, `100`) that don't exist in the ES PGC chart the app actually posts to → EBITDA split wrong, `saldo_caja` reads Capital social as cash. **confirmed (both).**
- Billing/Settings: pricing string 19/39/79 (settings UI) vs 29/59/119 (pricing page + backend PLANS, **verified**). **confirmed.**

**P-3 — User-selected categorization is silently discarded.** The same anti-pattern in two money modules: the chosen income/expense category never reaches the entry.
- Contabilidad: every entry posts to the same default account (`revenue_register.py:835,874`). **confirmed.**
- Costes: `RegistrarModal` never sends `category_id`; every manual gasto is uncategorized (`costes/page.jsx:302,322`). **confirmed.**

**P-4 — No error/failure state on data loads.** Failed fetches render as €0/empty/dashes rather than an error, in: Dashboard (`343-352`), Contabilidad (`457-487`), Costes (`Promise.all`, `404-413`), Finanzas (`loadSummary` swallows all errors, `312-324`), Clientes (approve/reject no feedback, `734-764`), Admin (most writes swallow errors, `1380-1470`), Settings, Marketing (`toggleStatus`/`Lanzar` silent). This is the single most pervasive UX defect.

**P-5 — Read-only modules / no create path.** Core CRUD "create" is missing in: Clientes (can't add a contact), Proyectos (can't create a project/task), HR (Contracts read-only — **confirmed**; vacations can be approved but never requested), Ventas (products create-only, no edit/stock adjust), Costes (no edit/delete gasto), Documentos (no edit-after-save), Settings (company data / notifications / password are UI-only stubs — **confirmed**).

**P-6 — Tenancy inconsistency in the billing/marketing seam.** Most modules correctly scope by `company_id`, but **Marketing scopes by `user_id`** (verified: `models/marketing.py:10,32,82` FK to `users.id`) — colleagues can't see each other's campaigns (**confirmed**), and Billing keys Subscription/TeamMember by `user_id`/`owner_user_id` while Vera Plus flips `companies.plan` by `company_id` — two tenancy models in one flow.

**P-7 — Duplicate / orphaned surfaces left in the tree.** Two full fiscal wizards (`/fiscal` and `/settings`) writing one config row with divergent IVA defaults (**confirmed**); duplicate prompt APIs (`/api/admin/prompts` vs orphaned `/api/backoffice/prompts`); legacy Vera stack (`vera/engine.py`, `vera/router.py`) still mounted, bypassing quota; orphaned `DashboardView.jsx` (496 lines) + `page.jsx.bak_*`; legacy `api/upload.py` writing incompatible rows into the shared `documents` table.

## 4. UX / Simplicity Themes (for a daily-use SMB operator)

1. **The primary daily action fails in most modules.** Reply to a customer (Clientes), register a categorized expense (Costes/Contabilidad), ring up a sale with correct tax (Ventas), invite a teammate (Settings) — each is the #1 reason an operator opens that screen, and each is broken. This is the dominant simplicity problem: the app is a dashboard, not a tool.
2. **Wrong numbers shown with confidence.** Ventas cart hardcodes 21% IVA for all products (**verified** `cartIva = cartSubtotal*0.21`, also for 10%/4%/0% goods) — **confirmed**; Finanzas shows Capital social as cash; Proyectos shows 0% complete on real projects; Costes KPIs (journal_entries) diverge from the gasto list (cost_entries); Marketing feeds the AI hardcoded zeros. An operator can't trust the figures.
3. **Filters/period selectors that don't filter.** Dashboard period filter re-scopes only 1 of 4 data sources; Costes category pills return 0; Historial/lists have no date filter or pagination. Controls imply capability they don't have.
4. **Silent failure everywhere (P-4).** No retry, no toast, no "something went wrong." For a non-technical owner this reads as "the app is empty/broken" with no recourse.
5. **Native browser primitives in a polished UI.** HR logs hours via `prompt()`; Documentos surfaces errors via raw `alert()`. Jarring and unbrandable.
6. **Identity confusion in the shell.** The sidebar/account shows a numeric user ID instead of name/email (**confirmed**) — the very first thing an operator sees is wrong.
7. **No drill-down from the headline KPIs.** Dashboard Ingresos/Gastos/Resultado aren't clickable — the natural next action is dead-ended.

## 5. Completeness Gaps (app-wide)

- **Billing is effectively free in current state**: global "beta" phase grants every tenant unlimited access (**confirmed**, `stripe_service.py:383-389`), and Vera Plus is never deactivated on cancellation (**confirmed**, `deactivate_vera_plus` is dead code at `:511`) — cancelled customers keep `plan='plus'` for free. No `stripe_subscription_id` persisted on the company, so dunning/reconciliation is impossible.
- **Team management is a non-feature**: invite 404s, member list never loads, "Eliminar" is dead (**confirmed**). No seat-limit enforcement, no extra-user billing path despite UI promising +€8/user.
- **Fiscal/DTE is simulated end-to-end**: certificate never used to sign, no transmission to Hacienda, no DTE history/PDF/anulación/compras, only El Salvador functional (**confirmed**).
- **CRM action loop unbuilt**: no create-contact, no KB/auto-response management, no email connect/sync — messages can only enter via a never-called endpoint (**confirmed**).
- **Proyectos is read-only**: no create/edit for projects, tasks, time, or expenses; no report download (**confirmed**).
- **HR creation paths missing**: Contracts read-only (**confirmed**); no employee edit; feedback/clima-laboral has no capture path so "empleados en riesgo" can never populate.
- **Ventas**: no customer linkage on sales (no `contact_id`), no receipt/ticket, no discounts, no e-invoice.
- **Documentos**: no human-review UI; evidence-pipeline tables (`extraction_runs/feedback/review_queue`) not created at startup, so the learning loop silently no-ops on a fresh DB (**confirmed**); `proyecciones_snapshots` (Finanzas) similarly depends on a manual script (**confirmed**).
- **Settings**: company profile, notifications, password change all persist nothing; no forgot/reset-password flow on login.
- **Marketing**: image generation, A/B plan, launch checklist generated but never persisted/shown; TikTok/Email offered but unsupported.
- **Admin**: Neo4j graph feature has backend but no UI button; no per-tenant selector for Profit Optimizer/Prospector.

## Per-module detail

### Dashboard  ·  health: **fair**
The dashboard is wired to real, existing backend endpoints and renders correctly with good empty/loading states, so it is broadly functional. However it has a broken Vera question handoff (typed questions are silently dropped), a period filter that is mostly cosmetic (only one of four data sources honors it), several mislabeled/computed-but-unused values, and a large orphaned duplicate component plus a backup file left in the tree.

**Findings:**
- **[HIGH/interconnection]** Vera question handoff is broken — typed/suggested questions are silently dropped — `app/dashboard/page.jsx:105` _(verify: confirmed)_  
  VeraHybrid.handleAsk() does sessionStorage.setItem('vera_pending_question', q) then calls onOpenChat() which runs openVeraDrawer({modulo:'dashboard'}). But grep shows 'vera_pending_question' is read by NO component — VeraDrawer.jsx never reads sessionStorage and openVeraDrawer only accepts {kpi, modulo, suggestions}. So when the user types a question in the Vera banner input and presses Enter/send, or clicks one of the 3 suggested questions, the drawer opens empty and the question is lost. The single most prominent interactive element on the dashboard (the AI input) does nothing useful.  
  → _Fix:_ Pass the question through openVeraDrawer (e.g. openVeraDrawer({modulo:'dashboard', initialQuestion:q})) and have VeraDrawer auto-send it on open, OR have VeraDrawer read+clear sessionStorage 'vera_pending_question' in a useEffect when it opens.
- **[MEDIUM/functionality]** Period filter is mostly cosmetic — 3 of 4 data sources ignore it — `app/dashboard/page.jsx:343-346`  
  The 'Periodo' SegmentedFilter (7d/30d/90d/year) only feeds /api/agente/resumen?period=${periodo}. /api/ventas/resumen, /api/clientes/analytics and /api/proyectos/resumen are fetched with no period param and return fixed windows (ventas: today + month-to-date best_sellers + last-14-days daily_revenue; clientes/proyectos: all-time). So changing the period only updates the top 4 KPI cards' Ingresos/Gastos/Resultado, while the bar chart (hardcoded 'últimos 14 días'), best sellers, status rows and module stats stay the same. Worse, the sparklines under the KPIs read resumen.series_14d which is ALWAYS 14 days regardless of the selected period, so a '7 días' or 'Año' selection shows a 14-day sparkline under a period-scoped number.  
  → _Fix:_ Either thread the period through ventas/clientes/proyectos endpoints (add ?period= and scope their queries), or scope the filter's UI/label to make clear it only affects the financial KPIs. At minimum make the bar chart title and sparkline window reflect the selected period.
- **[MEDIUM/completeness]** Orphaned duplicate dashboard component (496 lines) left in the tree — `components/dashboard/DashboardView.jsx:1`  
  components/dashboard/DashboardView.jsx is a full alternate dashboard (KpiCard, Sparkbar, fetches /api/agente/resumen, /api/ventas/resumen, /api/clientes/analytics, /api/proyectos/resumen, /api/clientes/inbox, /api/ventas/alertas/stock, /api/agente/chat). grep confirms it is imported nowhere — it is dead code that diverges from the live page.jsx (e.g. it hardcodes a light-only theme T and calls /api/clientes/inbox which the live page does not). It bloats the bundle source, risks being edited by mistake, and duplicates wiring that must be kept in sync.  
  → _Fix:_ Delete components/dashboard/DashboardView.jsx (and the directory if it becomes empty) or, if it is the intended future view, wire it in and remove the inline implementation from page.jsx.
- **[LOW/completeness]** Stale backup file committed/left next to the live page — `app/dashboard/page.jsx.bak_1779725231:1`  
  A 43KB backup app/dashboard/page.jsx.bak_1779725231 sits beside page.jsx. In the Next.js app router this file won't be routed, but it is clutter that also contains the same broken sessionStorage('vera_pending_question') code, and it can confuse future audits/edits.  
  → _Fix:_ Remove the .bak_* file from the working tree (and add app/**/*.bak* to .gitignore).
- **[LOW/functionality]** 'Ventas hoy' KPI sparkline plots transaction COUNT under a EUR value — `app/dashboard/page.jsx:496`  
  The 'Ventas hoy' card shows value = ventas.today.total_revenue in € (line 426/469), but its sparkline series is _serie.map(s => s.ventas || 0), where series_14d.ventas is the daily COUNT of sales (agent.py:162-166, COUNT(*) from sales). So the number is money and the trend line below it is units — inconsistent dimensions in the same KPI, and the green/red 'good' direction is computed off the count, not revenue.  
  → _Fix:_ Either add a per-day revenue field to series_14d for this card, or relabel the sparkline so it's clear it tracks number of sales, not revenue.
